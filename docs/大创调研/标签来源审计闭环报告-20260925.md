## 0. 本轮最重要的结论（先行摘要）

**结论一（好消息）：时间锚点档案的下载阻塞是误判，已解除。**
先前记录的"Figshare `ndownloader.figshare.com` 与 Zenodo API 均返回 403"**不成立**。真实情况是：`api.figshare.com/v2/file/download/<id>` 对部分文件 id 返回 404，而正确的下载端点是 **`https://ndownloader.figshare.com/files/<file_id>`**，它会 302 重定向到 S3 预签名地址。改用该端点后，v1 的**全部四个文件都可获取**。已实际下载并逐字节核验两个：

| 文件 | 官方字节数 | 官方 MD5 | 实测 MD5 | 结论 |
| --- | --- | --- | --- | --- |
| `LabelingOtherSources.tar.gz` | 2,483,382 | `9ddd1705ab6ae5650ca7e26091a3ba64` | 同左 | **逐字节一致** |
| `addresses.csv`（v1） | 6,914,875 | `d17b0a66c7469730caffc2486b1ea79c` | 同左 | **逐字节一致** |

**结论二（严重）：仓库在用的 `addresses.csv`（v3）与它所引用的 Figshare v1 工件，在内容与来源标注上都不等价。**
- 本机 `D:/Code/VSCode/Bitcoin_Transaction_Identification/bitcoin-dataset/addresses.csv`：6,911,449 字节，MD5 `0d5454323363580995839a439bd82e33`，SHA-256 `a451de6d9974594b0794284769d76c64ad92224ca010485d9265c9102feda283` → **这是 Figshare v3**，不是 v1。
- v1 → v3 的实际差异**只有一处**：380 行 `Defillama`(292)+`CoinMarketCap`(88) 被替换为 342 行 `Exchange`，**来源标签被抹去**（净 −38 行）。行索引证明这是**删行保留原索引**的增量修改，不是重新生成。
- 其余 **9,922 行 `BitcoinTalk` 记录在 v1 与 v3 中完全相同**，且**这批行在 v1 发布时就没有伴随的来源文件**——即 `addresses.csv` 本身就含有 `LabelingOtherSources.tar.gz` 无法追溯的记录。
- **后果：`addresses.csv` 的 `source` 列不能作为"逐来源许可"的可靠依据。** 至少 `Defillama`/`CoinMarketCap`/`Exchange` 三者之间的归属在 v3 里已不可恢复。

**结论三（严重）：`addresses.csv` 含约 9,922 行（9.6%）标签，其一手依据在公开工件中不可追溯。**
这 9,922 行分布为 PONZI 1,012 / EXCHANGE 2,373 / GAMBLING 4,718 / MINING 710 / MARKETPLACE 289 / FAUCET 401 / MIXER 188 / 空类 231，`entity` 多为 `satoshicircle`(1,648)、`Bitsler`(275)、`Cryptsy`(266)、`Ore-mine`(262)、`Mt.Gox`(254) 等。`LabelingOtherSources.tar.gz` 里**没有任何文件**覆盖这些记录。它们只能来自论文摘要中提到的**另一条未经发布的 BitcoinTalk 标注流程**（`gpt-4o-mini` 提取）。**该流程的输入、提示词、输出与人工校验记录，数据集作者均未公开。**

## 5. 地址到实体的映射规则

论文描述的四步：① 建立"ChatGPT 实体名 → 11 类"映射（参考 BitcoinTalk、互联网资源、Wayback Machine）；② 对每个已标注地址，将其可解锁 locking scripts 标为同标签；③ script 映射到 cluster/节点；④ **cluster 内含冲突标签则不标注**。

| 协议 §9 要求 | 论文做法 | 评价 |
| --- | --- | --- |
| 标签以原始地址/脚本证据投影 | 地址 → locking script → cluster | 方向一致，但论文止于最终 cluster，**未保留历史 `C_t` 映射** |
| 同一 cluster 内多类型记为冲突，不按多数票覆盖 | 论文**直接不标注**冲突 cluster | S1 须明确：沿用"移除"还是改为"标记冲突后按规则处理" |
| `-1` 保持未标注 | 未标注即无标签 | 一致 |

**关键缺口：** 论文的映射是「地址 → 最终 cluster」**一步式投影，无时间化 lineage**。本项目要在 `C_{T_j}` 上投影标签，必须自建「地址 → script → `C_{T_j}` 分量」映射。S0 冻结前缀已有 `script_id` 级 union provenance，**技术上可行**——这是本项目相对原论文的技术增量点。

**但本轮暴露了一个前置缺陷：** 该映射当前**完全缺失实现**——仓库无 base58/bech32 解码器、无标签证据锚点、无冲突检测。且由于 §2.4 的 9,922 行不可追溯，**任何"地址→实体"重建都无法对这 9.6% 给出可审计的一手依据**。

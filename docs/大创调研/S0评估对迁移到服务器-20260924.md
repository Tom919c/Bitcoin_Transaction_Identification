# S0 评估对迁移到实验室服务器

日期：2026-09-24。本文件记录 Gate 3A v1.3 S0 评估对（两次连续独立运行）从本机迁移到实验室 A100 服务器的决定、证据与后果。**这是一次有记录的取代（supersession），不是静默变更。**

## 1. 触发原因：本机无法可靠完成该作业

run02 在本机共失败三次：

| 尝试 | 启动 | 结束 | 历时 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 2026-09-22T22:36:00Z | 2026-09-23T09:25:58Z | 10h49m | 被宿主应用重启杀掉，无产物、无部分输出 |
| 2 | 2026-09-23T11:04:00Z | 2026-09-23T11:24:24Z | 20m24s | 主动停止（当时决定改用本地优先策略），无产物 |
| 3 | 2026-09-23T11:35:00Z | 2026-09-23T15:32:31Z | 3h57m | 再次被宿主应用重启杀掉，无产物 |

证据：`~/.workbuddy-ai/logs/startup/startup-2026-09-23.log` 的 mtime 分别为 17:25:58 与 23:32:31（+08），两次都对应 run02 的死亡时刻；机器未重启（`GetTickCount64` 显示 uptime 14.28h，开机于 2026-09-23 17:29）。失败后进程列表中已无 `python.exe` 实例。

结构性问题有三条，且互相独立：
1. WorkBuddy 桌面版每天重启 1–2 次，重启会连带杀掉会话的后台子进程；
2. `schtasks.exe` 在安全策略黑名单中，无法用计划任务让作业脱离宿主进程树；
3. `nohup` 从后台任务或前台调用 detach 都不继承免沙箱上下文，且子进程随调用结束被杀。

结论：**本机不适合承载单次约 10h42m 的作业**。三次尝试累计损失 15h07m。

## 2. 为什么必须两次一起迁移

评估产物 JSON 内嵌 `environment = {python, sqlite}`，且 `secondary.variation_of_information` 使用 `math.log`。本机环境为 `{3.12.3, 3.49.1}`，服务器为 `{3.12.14, 3.53.1}`；glibc 与 UCRT 的 libm 也不保证 `math.log` 逐位一致。finalizer 要求两次评估**逐字节相同**，因此跨主机的两次运行不可能通过该检查。

所以"把 run02 挪到服务器"在协议上等价于"两次都重跑到服务器"。已选择后者。

## 5. 后果与限制（须随结论一起报告）

1. 最终 S0 决策将建立在服务器两次运行之上，与本机 run01 的数值**不能做逐字节比较**；若两者数值出现差异，属跨解释器/跨 libm 的正常现象，须单独说明，不能作为"不一致"处理，也不能择优采用。
2. 本机 run01 的 `candidate=Go` 只作为独立参考：它说明在同一协议与同一输入下，**另一套环境**也给出了同一候选结论。这是稳健性证据，不是权威判定。
3. 若服务器两次运行未能逐字节一致，按协议**停止并审计实现**，不追加试验、不改阈值、不重跑筛选。
4. 服务器单次运行的耗时尚未实测；本机为 10h42m，服务器 CPU 在 Python 循环上快约 1.3 倍、但在大块 SHA-256 上慢约 3.2 倍，且 `/dev/sdb` 是机械阵列，故不能先验断定更快。

## 3. 标签何时公开、何时采集、是否更正（核心结论）

| 问题 | 答案 | 状态 |
| --- | --- | --- |
| 采集时间 | **2023 年底**（论文原文："We collected the data at the end of 2023"），从 546,440 个帖串收集 14,067,713 条消息 | 已核验（论文正文） |
| 逐标签公开时间 | **结构性缺失**。`addresses.csv` 字段已核验为 `address, entity, category, source` **四列，无任何日期或时间字段** | **已确认为缺失（非"未找到"）** |
| 逐标签采集时间 | **结构性缺失**，同上。仅批次级（2023 年底） | **已确认为缺失** |
| 是否更正/撤销 | 数据集有 v1→v2→v3 三次版本，但**未提供逐标签变更记录**；论文未描述版本化状态变化 | **未找到** |
| 唯一含日期的文件 | `BitcoinTalkThreads.tar.gz`，每条消息含 `date` 字段（**论坛发帖日期**） | 已核验（论文给出完整 JSON schema） |
| 图节点/边时间 | 仅**交易活动**区块索引（`first/last_transaction_in/out`、`reveal`、`last_seen`），非标签时间 | 已核验（论文表 1、表 2 + Figshare 说明） |

**这是一条比"未找到"更强的判定。** 先前只能写"未定位"，现在字段清单已核验：**`addresses.csv` 在结构上就没有时间列**。因此：

- 严格历史部署语义下的 S1 **不准入**，且这个结论**不会因为继续追查而改变**——数据本身不携带该信息；
- 唯一可用的时间锚点是 `BitcoinTalkThreads.tar.gz` 里**逐条消息的 `date` 字段**（论坛发帖日期），须与 `addresses.csv` 的 `entity` 名做连接才能推出候选公开时间；
- **发帖日期 ≠ 流水线首次发现时间**，也 ≠ 本项目采集时间。用它只能构造公开时间的**下界代理**，且需逐来源论证；
- 该代理只适用于 BitcoinTalk 来源（占 86.1%）；其余 13.9%（Montréal、Padua、SDN、WBTC 等）**无对应时间锚点**。

**这意味着上图第 3 节的核心结论两条必须同时成立才能做严格 S1：** 需要 `BitcoinTalkThreads.tar.gz` 与 `addresses.csv` 的实体名可连接；以及 13.9% 无锚点标签有明确的处理规则。这两条的可行性须在 10-02 准入报告中给出结论。

## 4. 地址到实体的映射规则（已核验）

论文描述：

1. 建立「ChatGPT 返回的实体名 → 预定义 11 类」的映射，参考 BitcoinTalk 相关帖串、其他互联网资源与 Internet Wayback Machine；
2. 对每个已标注地址，将其可解锁的 locking scripts 标注为同一标签；
3. 再将 script 对应到 cluster/节点；
4. **若一个 cluster 含多个冲突标签，则该 cluster 不标注。**

与协议 §9 的一致性检查：

| 协议 §9 要求 | 论文做法 | 评价 |
| --- | --- | --- |
| 标签以原始地址／脚本证据为起点投影 | 地址 → locking script → cluster | **方向一致**，但论文止于最终 cluster，**未保留历史 `C_t` 映射** |
| 同一 cluster 内多类型记为冲突，不按多数票覆盖 | 论文**直接不标注**冲突 cluster | 需在 S1 明确：是沿用"移除"还是改为"标记冲突后按规则处理" |
| `-1` 保持未标注 | 论文未标注的即无标签 | 一致 |

**关键缺口：** 论文的映射是「地址 → 最终 cluster」的一步式投影，**没有可重放的时间化 lineage**。本项目要在 `C_t` 上投影标签，就必须自己重建「地址 → script → `C_t` 分量」的映射，而这一步在 S0 的冻结前缀上**技术上可行**（S0 已有 `script_id` 级 union provenance）——这反而是本项目相对原论文的一个技术增量点。

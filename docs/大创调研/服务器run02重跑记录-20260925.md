## 2. 根因（含一次归因修正）

首次 run02 卡在 `folio_wait_bit_common`，当时机器上同时运行着 quan 自己的 ComfyUI 进程：

```
/home/chenquan/envs/comfy-cu130/bin/python /home/chenquan/ComfyUI/main.py \
  --listen 0.0.0.0 --port 8188 --reserve-vram 32 --disable-pinned-memory
```

**初判（不完整）**：把它当作干扰源，认为它带来 3.3 GB RSS、把 `buff/cache` 推到 94–102 GB，
导致 run02 的工作集被页缓存驱逐、每次访问都要回机械阵列（`/dev/sdb`，`ROTA=1`）重读。

**修正**：把 ComfyUI 停掉后重跑，启动速度仍是约 1%，说明该归因站不住。复审资源数据发现：

- `MemAvailable` 有 104 GB，最大用户进程 RSS 仅 37 MB —— **内存实际充足**，`MemFree` 低只是页缓存，
  这是 Linux 的正常且有益行为；
- 真正原因是**页缓存冷热差异**：run01 紧跟 21 GB 状态库传输之后，数据仍在页缓存中，故只用 1h15m43s；
  run02 从冷缓存开始做 4 KB 随机读，机械盘寻道成为瓶颈（稳态 `rchar` 约 2.4 MB/s，
  远低于顺序吞吐 87–92 MB/s）。

**这不是显存冲突**：run02 **用 0 显存**（已实测：`/proc/<pid>/fd` 中 nvidia 设备数 = 0，venv 无 torch，
`VmRSS = VmHWM = 318,720 kB`）。

**共享环境的操作边界**：该服务器是多用户共用环境，容器内还有其他用户。quan 已明确要求
**只能操作 chenquan 用户自己的进程与文件**，其他用户的一切不得触碰 —— 即使它们看起来在占资源。
资源竞争在共享环境里是常态，不是"问题"；正确反应是等，或者改自己的策略（例如把状态库复制到 SSD
避开机械盘寻道瓶颈），而不是去停别人的东西或调系统参数。本记录第 8 节所列的 SSD 备选方案即属此类。

**不能续跑**：冻结 runner 无进度日志、只在结束时一次性落盘，所以卡住的 run 无法恢复，只能从头重来。

## 5. 一个操作事故与教训

用 ssh 前台启动后台任务时，命令里含 `setsid nohup … & sleep N` 这类组合会被沙箱 **SIGTERM**（表现为
exit 1、无输出）。但此时**服务器侧进程其实已经起来了**。连续四次"失败"的启动累积出**四个并行实例**
（PID 185134/185137、185173/185176、185195/185198、185219/185222 各自成对），它们争抢同一个状态库的
I/O 并写同一个 `evaluation.json`。

处置：先杀父脚本（`run_s0_run02_retry`），再杀 `setsid` 脱离会话的 python 子进程；清空被污染的
`s0_run02_retry.log` / `.out` 与输出目录；重新启动一次并**不等待**，之后单独核查实例数确认为 1。

**教训**：ssh 前台命令里带 `&` + 长时间 `sleep` 不可靠。正确做法是发起后立即返回，隔一段时间用独立
命令核对进程。核对时必须 `grep -c` 计数，不能只看 `head -3`（四个实例时只显示前三个会漏判）。
